# bob — domain dictionary

> **Status:** implemented 2026-09-24; deployment evidence is tracked in [PR #135](https://github.com/EmelieHagander/Bob-the-builder/pull/135). **Project → optional Area → Step → Task** is the shared vocabulary and work model. The baseline audit below describes `1d4c984`; the implementation section supersedes its listed gaps. Existing Areas are not automatically reclassified.
> **Owns:** the canonical product meaning of Bob's core nouns and how those nouns relate to each other.  
> **Does not own:** database column/table names, RLS, page composition, or detailed domain behavior already owned by a specialist contract.

**Reading precedence:** the work hierarchy and terminology here supersede the older conceptual `Project → Area → Task` tree and a separate sequence of planning-only Steps. Existing runtime constraints still apply until migrated. Detailed evidence, history and authority rules in specialist contracts remain in force.

## Why this exists

Bob must not infer the meaning of words such as **Project**, **Area**, **Space**, **Task**, **Volunteer**, **Target** or **As-built** from generic English.

Those words have specific meaning inside bob. The same vocabulary should be understandable by:

- the person using bob;
- Bob's AI runtime;
- UI/product work;
- implementation sessions;
- tests and evals.

This dictionary is therefore **semantic product truth**, not a database catalogue.

Specialist documents still own detailed behavior. This file gives the short definition and points to the owning concept where useful.

## Runtime delivery direction

**Runtime delivery:** `src/domain/vocabulary.ts` owns the compact, versioned entries. `project-answer.ts`, the planner compiler/reviewer and CAD assistant add role-relevant subsets to their actual model calls. The marked table below is generated by `npm run sync:vocabulary`; CI runs `check:vocabulary`. The full audit is not pasted into prompts. Runtime tests observe model-call context and preserve the existing prompt-length budgets.

Do **not** create a mutable database dictionary yet.

The definitions below change with product decisions and code review, not per project. Putting them in a normal app table now would create another source of truth and a migration/admin problem without clear value.

When Bob's context implementation needs this vocabulary at runtime, prefer:

1. a small **server-owned typed domain dictionary** in code for stable machine-readable definitions/relations;
2. a compact **core vocabulary bundle** available to Bob every turn;
3. on-demand lookup for less common definitions when that keeps the prompt smaller.

A database-backed dictionary becomes justified only if definitions later need runtime curation/versioning without deploys. If that happens, it must have one clear owner and version semantics rather than silently diverging from this contract.

The runtime bundle must separate **meaning** from **capability**. In particular, it must not tell Bob that an Area-free Task or a Step phase can be saved while those writes are unsupported. The same versioned definitions should feed main Bob, the plan assistant/reviewer and the CAD assistant; relevant subsets may be smaller. Do not copy independent glossaries into their role prompts. The four cases below are evaluation fixtures, not always-loaded prompts or object-specific routing rules.

**No additional hierarchy:** Plan is the organisation of this Project's work, not a second copy of it. Phase, status, finish criteria, dates and responsibility are attributes or relationships. They are not extra containers between Step and Task. Instructions live inside a Task, not as another planning level.

**Names to retire as separate product nouns:** Workstream is a legacy alias for Area, not a new entity and not automatically a Step. Delprojekt is unnecessary for the Area grouping in this model. # Organisation and lifecycle

## Project

A **Project** is the shared container for one intended body of work.

It owns collaboration context such as members/volunteers, Areas, events and project-scoped planning records. A Project may be connected to persistent physical Building/Space/Element context, but the Project is **not the Building itself**.

A Project has one high-level lifecycle phase for the overall effort. Individual Areas may move through that lifecycle at different speeds.

**Not:** a room, a building, a task, or a permanent physical record.

Owner: [`project-phases.md`](project-phases.md) for lifecycle; `db/README.md` / runtime for persistence and authority.

## Project phase

The Project's overall maturity lens:

`Concept → Design → Planning → Build → Complete`

It tells Bob/UI what the overall project is trying to achieve now. It is not a substitute for Area phase, task status or Building state.

Owner: [`project-phases.md`](project-phases.md).

## Area

An **Area** is an optional Project-scoped grouping for a substantial body of related Steps. It is useful when a Project needs separate overview, responsibility or coordination for larger parts of the work.

An Area may be “Kitchen renovation”, “Exterior” or “Shared services”. It can follow a room or a work discipline, but is neither a room nor a mandatory folder for a small Project. Avoid empty Areas created only to satisfy a technical constraint.

An Area can map to a persistent physical Building/Space/Element target without becoming that physical object.

**Grouping recommendation:** each Step has one organisational home: directly in the Project or in one Area. Cross-Area dependencies and references do not clone a Step. Do not add recursive Areas or a second Subproject hierarchy without a demonstrated need. Existing Areas must be classified by their actual content: a row called “Sängen” may represent a Step in the intended model; its current table name does not decide its product meaning.

**Implementation:** `tasks.project_id` is the access/ownership root. `area_id` is nullable and follows the primary Step when one exists. Legacy Tasks without a primary Step remain visible as work to organise.

**Not:** a persistent Space in the Building model.

Owner: [`project-phases.md`](project-phases.md) for phase semantics; [`building-model.md`](building-model.md) for Area ↔ physical-target distinction.

## Area phase

The lifecycle position of one Area/workstream using the same phase vocabulary as the Project where useful.

Example inside one renovation Project:

- Bedroom — `Complete`
- Office — `Build`
- Guest room — `Design`

The Project may still be broadly `Build` while these Area phases differ.

Project, Area and Step have separate phase fields. Step phase is nullable and versioned with the plan, so a bed frame can be in Build while its drawers are in Design. Readiness uses Step phase when set, otherwise Area phase. Area overview may show mixed progress; do not force all children into one phase or require users to maintain three copies of the same status.

## Project Plan

A **Project Plan** is the evolving organisation of the Project's Areas, Steps, Tasks, dependencies and relevant schedule, with goals and finish criteria. It covers the route from idea to finished work, refining near-term work while later work may remain coarse. Bob maintains it from the actual project goal, evidence and constraints.

The current versioned plan record stores an ordered Step sequence. That is an implementation seam to integrate with the rest of the work, not a second plan. Display order alone is not a dependency or a ban on parallel work. "Plan" here means the work plan; a floor plan is a Drawing.

## Plan Step

A **Step** (technical alias **Plan Step**) is a coherent piece of work with an understandable result: “Sängen”, “Golvet” or “Grundläggning”. Its title may name the result or the work; its goal makes the finish explicit. It is not restricted to a physical object: project-wide survey, preparation or handover can also be a Step when they have real work and a clear result.

A Step contains executable Tasks and carries a goal, state, brief, responsibility and finish criteria. It may link to a physical component or CAD assembly without being that object. A numbered list position does not mean the previous Step must finish first.

Recommended interpretation: keep a Step's identity through design, planning, construction and verification. Do not create parallel “design the drawers” and “build the drawers” planning trees when Tasks and phase within the same Step suffice. Split work when responsibility, dependencies or a separately verifiable result justify it, not at a fixed number of tasks.

**Implementation:** Steps have one optional Area and can be active concurrently. `project_plans.focus_step_id` records Bob’s current focus without changing execution state. `tasks.primary_step_id` distinguishes ownership from related-work links.

## Step Brief

A **Step Brief** is Bob's compact self-prompt for the current Step: purpose, focus, important constraints and what matters while working there.

It is working guidance, not project evidence. Structured project facts and Completion Requirement state outrank it.

## Completion Requirement

A **Completion Requirement** is one structured condition that must be true before Bob may judge a Plan Step complete.

Tasks are actions; Completion Requirements are finish criteria. A completed Task does not automatically satisfy or complete a Step. Requirements are satisfied, conflicted or made stale by project evidence.

Owner: [`living-project-plan.md`](living-project-plan.md).

## Task

A **Task** is one executable, assignable action contributing to a Step, such as measuring and cutting stock, producing a drawing or assembling a frame. It can be performed by a person/crew or, for digital work, Bob. It need not be a physical construction action.

Tasks describe work people can perform/assign/track. Their operational state is task status (`todo`, `doing`, `done`, `blocked`), not Project phase.

A Task is not a completion criterion; the Step's Completion Requirements remain the finish test. Ownership: one primary Step, with references to other affected work when useful. One shared action is still one Task, with one status and one accounting of effort. Unorganised existing Tasks remain visible during migration; do not delete them or invent a completed plan around them.

**Implementation:** a Task belongs to its Project and has at most one primary Step. Tasks without one are explicitly unorganised; legacy Area-only creation remains compatible. New Step tasks use `create_work_task` or Bob’s `save_project_task`. `link_project_plan_task` can move ownership or add a reference without duplicating the Task. Task dependencies, needs and readiness remain the same foundation.

**Not:** a Project phase, Plan Step, Completion Requirement or physical Building element.

## Task step

A **Task step** is the legacy technical name for an ordered **instruction/checkpoint** inside one Task. Use “Instruktion” or “Kontrollpunkt” in product language so it cannot be mistaken for a Plan Step.

It can carry instructions, completion state and media. It is more specific than the Task and should not become its own project/workstream lifecycle.

## Phase, status, readiness and focus

Lifecycle labels: **Idé → Design → Planering → Bygg → Klart**, corresponding to the existing `concept/design/planning/build/complete` codes. Design decides what/how to construct; Planning organises quantities, tasks, people, resources and timing. They may overlap or be revisited; a fixed phase vocabulary is not a hardcoded recipe for every construction.

Task status (`todo/doing/done/blocked`) and current plan-Step state (`planned/active/blocked/completed`) describe execution state. Readiness describes prerequisites. A drawing can be complete while a construction Task remains blocked. A Project being in Build does not make every Task ready.

**Bob focus** is the work Bob is concentrating on now, not the only work people may execute. Recommended parallel execution must separate that focus from Step state. **Complete** is a work outcome; **as-built** is evidence of the physical result, not a synonym automatically assigned by task checkboxes.

## Dependency and completion

A **Dependency** is a directed prerequisite, possibly across Steps or Areas in the same Project. For example, a floor task can wait for a services task. Sequence/position is merely presentation unless a dependency is recorded. Existing runtime dependency checkpoints refer to `task_steps`, not living-plan Steps; a Step dependency graph is not already implemented by that field name.

A **Completion Requirement** belongs on the work it verifies, not as a new hierarchy level. “All Tasks done” and “result verified” may differ. Evidence and unresolved conditions must remain visible without turning every ordinary action into an approval request.

# People and collaboration

## Person / project member

A **Person** is a participant represented inside one Project's crew.

A signed-in project member may have authenticated project access. Person records can also represent project participants whose product role is not the same thing as backend authority.

Skills/roles are project information, not proof of professional certification.

## Volunteer

A **Volunteer** is a project participant helping with the work.

Bob currently has two relevant access shapes:

- a normal signed-in Project member/crew participant;
- a prepared name-only, project-limited volunteer flow where the person does not need a full Auth account.

“Volunteer” describes participation, not a universal permission level and not professional competence.

Owner: `Docs/user-stories.md` + `db/README.md` for access behavior.

## Skill

A **Skill** is a project-recorded capability/experience label for a Person.

Bob may use it to help match people to work, but it must not silently promote someone into a licensed/certified professional.

## Event / build day

An **Event** is a Project-scoped planned gathering/build day with attendance context.

It is coordination context, not the Project phase itself.

**Assignment** says who performs a Task. **Responsibility** says who owns a result/follow-up. **Attendance** says who will be there on a build day. None of these alone grants backend access or proves professional competence. A day's work is a view/allocation of existing Tasks, not copied Tasks with a fresh completion history each morning.

# Physical place

## Site

A **Site** is a persistent physical place that may contain one or more Buildings and may outlive individual Projects.

## Building

A **Building** is the persistent identity of a physical building.

It can accumulate better knowledge across Projects. The Building is not reset when a Project ends.

## Level

A **Level** is an optional grouping inside a Building, such as a floor/storey.

## Space

A **Space** is a persistent physical room/space within a Building.

A Space is not an Area. Several Projects may touch the same Space over time; one Project Area may point to a Space as its physical target.

## Building element

A **BuildingElement** is a persistent physical component/element such as a wall, opening, door, window or other explicitly modelled element.

## Physical scope

**Physical scope** says which Site/Building/Space/Element a Project or Area applies to.

It answers **where in reality** the work belongs.

Owner: [`building-model.md`](building-model.md).

The same phrase can name different linked entities: “Köket” can be a persistent Space and an Area for this renovation. A veranda extension does not automatically become a separate Building. A freestanding animal house may be a Building; its construction Project is a different identity. Do not force a physical classification from a project title alone.

## Building state

The lifecycle of physical truth for a Space/Element/relationship:

- **current / as-is** — accepted reality now;
- **proposed** — an intended possible change;
- **accepted / as-built** — confirmed physical result after change.

Building state is independent from Project/Area phase.

Owner: [`building-model.md`](building-model.md).

# Evidence and design

## Media asset

A **MediaAsset** is a durable Project image with purpose/provenance and optional links to Area/Task/Step.

Purposes include current state, reference, instruction, proposal, progress and as-built.

A photo can be evidence without proving a measurement.

Owner: [`media-and-steps.md`](media-and-steps.md).

## Measurement

A **Measurement** is a revisioned numeric project fact with unit, subject and provenance/truth state.

A measured value, provided specification, estimate and unknown are different truth classes.

Owner: [`project-facts.md`](project-facts.md).

## Existing component

An **ExistingComponent** is a known physical thing already present/owned that may be inspected, reused, removed or replaced.

“Reuse” intent does not itself certify suitability.

Owner: [`project-facts.md`](project-facts.md).

## Solution

A **Solution** is one design alternative for how to achieve the Project/Area intent.

Solutions are revisioned and may keep assumptions, trade-offs, images and pinned evidence.

Owner: [`solutions.md`](solutions.md).

## Selected target

A **Selected target** is the explicit Solution revision the work is currently intended to build toward.

It is an intent/decision pointer, not professional approval.

**Current implementation:** Project- and Area-scoped target selection exists in `20260914164000_project_area_phases_and_scoped_targets.sql`; the older claim that all targets are project-global is superseded. This does not imply independent Step-scoped target selection exists. Adapting targets when a legacy Area becomes a Step is part of the migration review.

Owner: [`solutions.md`](solutions.md) for current behavior; [`project-phases.md`](project-phases.md) for the multi-Area implication.

## Artifact / drawing

An **Artifact** is a revisioned Project output such as a drawing, elevation, section or detail. Use the concrete user-facing kind (“Ritning”, “Snitt”, etc.) rather than requiring the user to learn “Artifact”.

It pins the selected target and exact measurement evidence used by that revision and carries concept/measured/build-ready status.

Owner: [`artifacts.md`](artifacts.md).

## Assembly, part and illustration

An **Assembly** is a designed construction made of related part instances. A **Part definition** describes a reusable kind of part; a **Part instance** is one occurrence in a particular assembly. These belong to the CAD/material model, not the work hierarchy. A Step can concern an assembly, and several Tasks can work on the same parts. A physical ExistingComponent or BuildingElement is not silently replaced by a CAD instance.

An **Illustration/mockup** conveys appearance or an explanation. A **Drawing** conveys the construction at its stated fidelity. Neither a realistic image nor a successful CAD render proves physical measurement, suitability or completed work. The CAD exchange file type **STEP** has no relationship to a project's **Step**.

Owners: [`cad-adapter.md`](cad-adapter.md), [`material-assembly-use-case.md`](material-assembly-use-case.md), [`material-catalog.md`](material-catalog.md). These own their implementation limits; this definition does not assert a complete BOM/stock workflow exists.

# Materials and execution

## Material requirement

A **MaterialRequirement** is the canonical planning record for how much of something the selected solution/work needs.

It retains basis/method, selected-target lineage, optional drawing lineage, allowance and stock/reuse deductions.

This is different from a Shopping item.

Owner: [`material-planning.md`](material-planning.md).

## Stock item

A **StockItem** is material the Project already has available/inspect/unavailable before new purchasing.

## Shopping item

A **Shopping item** is the existing checkable purchasing surface.

A MaterialRequirement may be explicitly published/updated into Shopping. Shopping remains independently editable and is not the calculation authority.

## BOM / material plan

“BOM” or **material plan** means the set of material requirements derived/recorded for the intended work, including transparent quantity basis and existing stock/reuse where modelled.

It must not be confused with the legacy free-form `materials` records alone.

## Readiness

**Readiness** answers whether a piece of work has enough evidence, decisions, prerequisites/materials/tools/dependencies to proceed at the claimed fidelity.

Readiness is not automatically the same as Project phase, Area phase or Task status.

# Bob context words

## Current View

**Current View** is the server-grounded semantic description of what the person is looking at now: page/surface plus the authorised focused Project/Area/Task/Step/etc.

The browser may send pointers; the backend hydrates facts.

Owner: [`ask-bob-context.md`](ask-bob-context.md).

## Project Catalog

The **Project Catalog** is a small navigation inventory telling Bob which kinds of project context exist and where, without loading all record bodies.

Owner: [`ask-bob-context.md`](ask-bob-context.md).

## Project truth

**Project truth** is persisted, authorised information about this Project/Building context with its real provenance/truth state.

Prior Bob conversation and general construction knowledge are never substitutes for fresh Project truth.

## General construction knowledge

Reusable construction methods/guidance that are not facts about this Project.

Future source-backed Building Knowledge Library content belongs to this class and must remain distinct from Project truth.

# Relationship summary

| Relationship | Intended meaning | Current implementation boundary |
|---|---|---|
| Project → Area → Step → Task | Area is optional; work has an organisational home | Explicit Project + nullable primary Step/Area; secondary links are references |
| Project → Step → Task | Small projects need no placeholder Area | Supported through primary_step_id with null area_id |
| Task → instructions/checkpoints | Guidance within the Task | `task_steps`, distinct from plan Steps |
| Step/Task → dependencies | Cross-scope ordering without duplicated work | Task dependency foundation exists; plan-Step dependency graph does not |
| Project/Area/Step → phase | Lifecycle lens, with independently progressing scopes | Project/Area fields and versioned nullable Step phase |
| Work → physical scope | Where/what in reality this work concerns | Building/Space/Element links are not work parents |
| Work → underlag | Reuse the same revisioned drawing/image/evidence at relevant work | Supported scopes vary by record kind; do not invent an arbitrary universal attachment API |
| Task → people / build days | Responsibility, assignment and schedule | Exact current scheduling capabilities remain owned by collaboration/runtime contracts |

The migration supplies this ownership model. Unorganised work is an explicit compatibility state, not a guessed hierarchy.

# Four project checks — proposed examples, not templates

These cases test whether the vocabulary scales. They are organisational examples, not technical construction specifications, approved project plans or fixed lists every project must receive. All four can move through Idé, Design, Planering, Bygg and Klart without replacing their work identities at each phase.

| Project | Area grouping | Example Steps | Example Task within a Step |
|---|---|---|---|
| Våningssäng med lådor | Usually none | Sängen; Bokhyllan; Stegen; Lådorna | Sängen → Mäta och kapa virket; Ytbehandla; Skruva ihop |
| Veranda | Usually none for one veranda; optional if scope warrants separate organisation | Grundläggning; Bjälklag; Golv; Tak; Räcke | Bjälklag → Kapa reglar enligt kaplistan |
| Renovera huset | Köket; Badrummet; Klimatskal; Gemensamma installationer | Köket → Rivning; Golvet; Köksinredningen. Klimatskal → Tak; Fasad; Fönster | Köket → Golvet → Lägg undergolvet |
| Höns-/kaninhus | None for one small structure; separate Areas for shared structure and animal sections if the project actually includes them | Grund; Stomme; Tak; Inredning; Utegård | Utegård → Montera nät enligt ritningen |

**Bunk bed:** “Sängen” is a Step because it is a coherent result within this Project. Its CAD assembly is a linked representation, not another work Step. The three drawers can share a Step with several Tasks; separate drawer Steps only when independent work/control makes that useful. Planning Tasks, such as producing the drawing, live with the same Step as later build Tasks. Their proposed sequence is checked against the actual construction rather than blindly treating every list position as a dependency.

**Veranda:** the Project is the change being made; its physical relation to the house belongs in building context. Roof and railing work may progress independently when their prerequisites allow. A shared site-preparation Step can exist directly under the Project. A future larger extension can add Areas without replacing the existing Task/media identities.

**House renovation:** an Area needs several meaningful Steps, not simply a bigger name. Avoid creating both an “El” Area and copied electrical Tasks in every room. Choose one owning location for each action and link dependencies to affected rooms/work. Kitchen floor work may wait for a Task in shared installations; completed work elsewhere stays complete. Cross-project dependencies are outside this review's proposed implementation scope.

**Animal house:** the vocabulary does not assume that chickens and rabbits share accommodation. If the brief contains two sections, group them and their shared structure explicitly; if it is one small house, skip Areas. Two people can work on roof and interior while another Task waits for materials. Species-specific requirements are project content to investigate, never a hardcoded vocabulary branch.

**Scale rule:** classify relative to the project scope. A veranda can be its own Project or an Area in a house renovation. A bed frame can be a Step in a bunk-bed Project. Do not assign permanent levels based on object names. Keep construction details in linked assemblies/parts rather than growing an arbitrarily deep work hierarchy.

# Implementation — shared vocabulary and unified work

`20260924135637_unified_project_work.sql` implements the ownership/access migration and preserves Task IDs, status, assignments, instructions, evidence and history. Only one unambiguous, same-Area current Step link becomes primary automatically. Multiple or cross-Area links remain references. Existing Areas are never converted into Steps by name.

- `project_work_read` is the common Project → Area/Step → Task projection. The Plan surface shows it, plus unorganised work, without a second Workstreams tree. Task pages return to the owning Step.
- Plan compilation stages primary Task links by Step position; proposal approval applies them atomically and rejects stale Task timestamps. Approval does not complete Tasks or invent evidence.
- Task access, research, media, instructions, materials, dependencies, Today/readiness and volunteer functions use explicit Task Project scope. Optional Area no longer removes a Task from those paths.
- Bob can create/update Areas, create/revise Tasks in a primary Step, move/reference Tasks and set focus through the existing claimed-turn write ledger. Same-project authority, request provenance, revision checks and retry readback remain enforced.
- A separate Step phase is stored on plan revisions. Multiple active Steps are allowed; changing focus changes no execution state.

**Remaining boundaries:** this does not reclassify the owner’s existing project automatically, introduce recursive Areas, add a Step dependency graph, or add universal Step-scoped physical targets. Existing targets, measurements and attachments retain their supported scopes. The four SQL fixtures prove data paths, not unconstrained live-model planning quality across all construction projects.

**Verification:** `tests/unified-project-work.test.ts` exercises all four project shapes, ordinary-member writes, staged approval, migration backfill, project isolation and registration-free volunteers. Main/planner/reviewer/CAD tests observe the vocabulary on actual mocked model calls. `scripts/check-project-work-browser.mjs` checks live-config React/data paths using HTTP fixtures, creation and reload at phone/desktop sizes. Production verification is recorded separately in [PR #135](https://github.com/EmelieHagander/Bob-the-builder/pull/135).

## Ambiguous words to disambiguate at boundaries

| Word today | Distinct meanings that must remain explicit |
|---|---|
| Plan | Work plan versus a plan-view/floor-plan Drawing |
| Step | Project work Step versus Task instruction/checkpoint versus CAD STEP file |
| Area / room | Project work grouping versus persistent Space |
| Target | Chosen Solution revision versus physical scope versus media-link destination versus the owner's desired outcome |
| Requirement | Step finish criterion versus material quantity requirement versus a product user story |
| Component / part | Existing owned thing versus BuildingElement versus CAD part definition/instance |
| Material | Material definition/specification versus required quantity versus available stock versus shopping line |
| Ready / complete / approved | Prerequisites sufficient versus work finished versus a recorded decision; none automatically proves physical safety or as-built state |
| Person / user / volunteer | Project participant versus authenticated identity versus participation/access flow |

## Migration and delivery principles

1. Use this dictionary for product/implementation decisions; record accepted refinements here. Keep the role prompt short and do not paste the entire audit into Bob.
2. Inventory every existing Area/Step/Task and its links. Produce an explicit old-ID → preserved/new-ID mapping before transforming anything. Do not treat every Area as a Step or every plan Step as a Task.
3. Establish the ownership contract and caller-authorised read/write paths for Project → optional Area → Step → Task. Cover RLS, volunteer scope, physical scope, targets, measurements, materials, CAD, media, assignments and history. Area-to-Step conversion must not cascade-delete its children or orphan its selected target.
4. Adapt plan compilation and linked writes, shared runtime vocabulary and the read projection together. Reuse completed work, evidence and exact versions. The vocabulary bundle states current capabilities explicitly during transition.
5. Consolidate the UI around that projection. Unlinked/partially migrated work remains visible. One drawing can be referenced in multiple work locations without duplicate files or conflicting completion states.
6. Separate focus, phase, status, readiness and dependencies so parallel work can be represented honestly. No multiplication of user approval prompts is implied by these concepts.

## Acceptance for a shared vocabulary

- Main Bob, planner/reviewer and CAD receive matching vocabulary-version metadata and applicable definitions; a test observes the actual model-call input, not just a file on disk.
- Repeat the four project cases with ordinary wording and varied object names. Bob chooses appropriate granularity and optional Areas without object-name dispatch or fixed construction scripts.
- A small Project works without an invented placeholder Area; a house renovation uses Areas while a project-wide Step can remain directly under the Project.
- Moving/grouping work preserves task completion, people, media, drawings, evidence and history. A shared Task is not counted twice.
- Several independent Steps can progress concurrently; a genuine dependency blocks only the affected work. Bob's focus does not imply that all other work must stop.
- A participant opens the same Task from a Step and a build day and sees the same instructions and current linked underlag after reload.
- Documentation, the UI label and the tool/data identity agree about which kind of Step/target/requirement is meant. Renaming text alone does not satisfy this acceptance.

# Maintenance rule

Keep accepted meanings, implemented behavior and deployed verification distinct. Edit shared entries in `src/domain/vocabulary.ts`, regenerate this table, and keep the version and actual-call tests aligned. Do not hand-maintain a second list of overlapping definitions or imply that a source commit proves production deployment.

Do not copy detailed schema or domain rules into this dictionary. Link to the owning contract instead.
